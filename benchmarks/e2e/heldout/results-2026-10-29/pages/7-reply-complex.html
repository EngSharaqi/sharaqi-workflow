I've implemented the resolver in `src/resolve.js` and added tests in `test/resolve.test.js`. `npm test` passes all 32 tests. Nothing is committed.

**How it works**
- **Order:** root entries come first, in order. Each package a selected version needs is added to the end of the list the first time it appears, which gives the breadth-first order you specified.
- **Choosing a version:** when the resolver reaches a package, it takes the newest version that matches every range known so far. A version is skipped if one of its ranges fails for a package that's already selected, including itself (this is how cycles are handled). It's also skipped if it depends on a package that isn't in the registry.
- **Backing up:** if a package has no usable version left, the resolver steps back and tries the next older version of the previous package. Each step is undone exactly: its ranges, the packages it brought in, and its selection. So a package needed only by a version that was later abandoned never shows up in the result. The search uses its own stack rather than recursion, so long dependency chains can't overflow the call stack.

**Judgement calls**
- **When ranges are checked:** a version's dependency ranges are parsed when it's tried as a candidate, before the missing-package check. Versions that are never tried are never parsed, so a bad range in a version that isn't reached doesn't throw.
- **No look-ahead:** I deliberately didn't make the resolver check ahead for doomed packages. Skipping work early would change which versions get tried, and so which bad ranges throw a `TypeError`. The cost is that the worst case is exponential, which is inherent to this way of searching.
- **ERESOLVE message:** it names the package from the most recent conflict and says why, for example `no version satisfies ^2.0.0 (from root), ...` or `a@1.0.0 requires ^1.0.0, but c@2.0.0 is selected`. That package is also set on `err.package`.
- **Version format:** I read the format strictly. Leading zeros (`01.2.3`) and spaces after an operator (`> 1.2.3`) are invalid ranges. Registry version keys that aren't valid `MAJOR.MINOR.PATCH` are ignored. Version numbers are compared as BigInts, so very large numbers still compare correctly.
- **Odd package names:** names like `__proto__` or `constructor` are handled safely, and the result is a plain object with its keys in the order the packages were first needed.

**Tests** cover every range form and invalid input, transitive dependencies, ranges added after a package was already selected, backtracking, dropping abandoned packages, the breadth-first order, cycles, missing packages, both error codes, and that the inputs are left unchanged. There's also a comparison against a simple recursive version of the same rules on 400 random registries. In about 50 of those the resolver returned a solution, and it had to match the recursive version exactly, including key order. In the rest it had to throw `ERESOLVE`.
